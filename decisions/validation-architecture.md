# Validation Architecture

Decisions made 2026-05-29.
Goal: prevent document rejection by Moroccan courts before the user prints.

---

## Why papers get rejected — fixed list of causes

All checkable programmatically. Court clerks (كتّاب الضبط) and notaries reject for:

1. **تفقيط mismatch** — amount in digits ≠ amount in words (most common rejection)
2. **CIN format wrong** — must be `[A-Z]{1,2}[0-9]{6}` (e.g. B123456, AB123456)
3. **Date logic broken** — end before start, signing date in future, blank date
4. **Parties are the same person** — signer CIN = receiver CIN (invalid for most doc types)
5. **Required fields blank** — clerks stamp "ناقص البيانات" and return same day
6. **Wrong doc type for the legal act** — only partially detectable; use `legal_review` badge

---

## تفقيط (amount-in-words) validation

Critical. Every monetary amount must appear twice: digits AND Arabic words. Mismatch = void.

> مبلغ **50,000** درهم (**خمسون ألف** درهم)

`tafqit` libraries exist in Python and JS. Approach:
- Template declares two fields: `price_digits` (type: currency) and `price_words` (type: text)
- Cross-validator `tafqit_match` runs before print: convert `price_digits` to Arabic words,
  compare to `price_words` — warn if mismatch, block print if required

## Declarative validator schema (all in JSON, zero hardcoding in JS)

### Field-level — in `field-spec.v1.json`:
```json
"field_types": {
  "cin":      { "pattern": "[A-Z]{1,2}[0-9]{6}", "error_ar": "صيغة البطاقة الوطنية غير صحيحة" },
  "currency": { "min": 0.01, "error_ar": "يجب أن يكون المبلغ أكبر من الصفر" },
  "date":     { "not_empty": true, "error_ar": "التاريخ مطلوب" },
  "phone":    { "pattern": "0[67][0-9]{8}", "error_ar": "رقم الهاتف غير صحيح" }
}
```

### Cross-field — in `templates/{id}.json`:
```json
"cross_validators": [
  {
    "type": "date_order",
    "before": "start_date", "after": "end_date",
    "error_ar": "تاريخ النهاية يجب أن يكون بعد تاريخ البداية"
  },
  {
    "type": "parties_differ",
    "fields": ["seller_cin", "buyer_cin"],
    "error_ar": "البائع والمشتري لا يمكن أن يكونا نفس الشخص"
  },
  {
    "type": "tafqit_match",
    "amount_field": "price_digits", "words_field": "price_words",
    "error_ar": "المبلغ بالأرقام لا يطابق المبلغ بالحروف"
  }
]
```

## validate.js — client-side (runs before print)

Reads field declarations + cross_validators from template JSON.
Highlights invalid fields in red, shows error message in Arabic, blocks print button.
Zero hardcoded rules — all driven by the JSON above.

## validate.py — template authoring (runs at build time)

Same logic, Python. Used by `audit_template.py` and `build.py`.
Catches authoring errors before a template ships:
- Field count > 0
- Required fields declared where "ب.ت.و" / amounts appear in template text
- Cross-validators reference fields that actually exist
- No date field left without a cross-validator when two dates are present

## legal_review workflow

```json
"legal_review": {
  "status": "pending",   // pending | reviewed | approved
  "reviewer": null,      // name or firm when reviewed
  "reviewed_at": null,
  "notes": ""
}
```

- `pending` → show yellow badge: "⚠ لم يُراجَع من قِبَل محامٍ"
- `reviewed` → show blue badge: "راجعه محامٍ — للاستخدام المرجعي فقط"
- `approved` → no badge (clean)

Templates generated by us start as `pending`. Drive-imported templates also `pending`.
A Moroccan lawyer reviewing and signing off = `approved`.
